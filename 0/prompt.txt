## Review

### Central defect shared by all `dependency-*` rules (dependency-helpers.js)
**High.** Everything hinges on the regex `^[A-Z][A-Za-z0-9]*Dep$` (dependency-helpers.js:1). This is a naming heuristic standing in for the architectural concept "dependency wrapper type," not type-based detection. Consequences ripple through every rule below:
- Any interface ending in `Dep` that isn't actually a DI wrapper (e.g. `LaptopDep` meaning "deprecated laptop") gets swept in — false positive.
- A real wrapper aliased/re-exported under a non-`Dep` name (`export type { TimeDep as Clock }`, or `import { TimeDep as T }`) is invisible — false negative.
- No use of the type checker: `AppDeps = TimeDep &amp; LoggerDep` resolved through an imported type alias in another file is never expanded (docs admit this for `dependency-parameter-convention` but the same hole exists in `sort-dependency-types` and `no-over-depending`).
**Redesign:** detect the pattern structurally/semantically — e.g. via `@code-architecture/dependency-wrapper` JSDoc tag, a branded marker type, or TS type-checker introspection (does the type have exactly one readonly member and is it used as an object-capability contract) — rather than a `*Dep` suffix regex. At minimum, make the suffix configurable instead of hard-coded so consumers aren't forced to name everything `XyzDep`.

### dependency-parameter-convention — High
- False negative: `dependencyParameter` only scans `node.params` directly; a dependency type buried in a destructured parameter (`({ deps }: { deps: TimeDep })`) or in a generic constraint isn't an `Identifier`/simple param, so `dependency.parameter.type !== "Identifier"` reports `nameDeps` even for legitimate curried style, while true violations via `function f(x: TimeDep, y: TimeDep)` (two references, same wrapper) collapse to one `dependencyArguments` check that still works, but `function f({time}: TimeDep)` bypasses the "named deps" check entirely since destructured patterns are `ObjectPattern`, not `Identifier` — reported as `nameDeps` even though there's no way to satisfy it structurally without renaming, forcing an awkward `(deps: TimeDep) =&gt; { const {time} = deps; ... }` workaround. Not documented as a limitation.
- Overloads: `TSDeclareFunction` (ambient overload signatures) aren't in the `:function` selector set typically, but `TSEmptyBodyFunctionExpression`/interface method signatures with `Dep` params (e.g. inside a `TSInterfaceDeclaration` method) are visited too, incorrectly forcing `deps` naming convention onto interface method declarations where no implementation curry story exists.
- Docs claim "does not resolve aliases such as `AppDeps`" — accurate, but this materially defeats the rule for any real codebase using aggregate `AppDeps` types, which the sibling rules' own examples promote. This is a fundamental architecture gap, not a corner case.

### dependency-wrapper-shape — High
- False positive: any interface named e.g. `LookupDep` where "Lookup" is unrelated to dependency injection ("a `Dep`-suffixed lookup table type") is force-shaped into a DI wrapper. Purely nominal.
- False negative: a wrapper written as `export interface TimeDep extends BaseDep {}` (member inherited via `extends`, zero own members) — `members.length !== 1` fires `singleProperty` even though it may be a legitimate re-export-with-narrowing pattern; conversely, a `type TimeDep = SomeOtherAlias` (not a `TSTypeLiteral`) silently returns `null` from `wrapperMembers` and is never checked — a completely unchecked escape hatch for a `*Dep`-suffixed alias.
- `memberType.typeArguments?.params.length &gt; 0` rejects any wrapper property typed with generics, e.g. `readonly time: Time&lt;Utc&gt;` — a legitimate parameterized capability type — reported as wrong `propertyType` with a message that says "must wrap the 'Time' dependency type" even though it does, just parameterized.
- Naming coupling: property name and wrapped type name are *derived* from the wrapper's own name via string slicing (`name.slice(0, -3)`, lowercase first letter). `AbcDep` must expose exactly `abc: Abc`. This directly violates the plugin owner's goal — it forces every dependency wrapper's file-local names into a fixed lockstep triple, not a generic architectural shape ("exactly one readonly member, name matches the type it wraps" could be checked without asserting *what* the name must be, e.g. by comparing member key derived from type name generically already — but it forbids `readonly clockService: Clock` for `ClockDep`, which is still an unambiguous, non-clashing single-property wrapper).

### no-over-depending — Medium/High
- False negative (high): `used` tracking only recognizes `MemberExpression` on an identifier literally named `deps` (`node.object.name !== "deps"`). Destructuring `const { time } = deps;` then using `time.now()` never touches `deps.time` as a MemberExpression, so `no-over-depending` cannot see the use and will report `unusedDependency` for something actually used — false positive triggered by an idiomatic destructuring style the wrapper-shape/parameter-convention rules elsewhere don't forbid.
- False negative: aliasing `const d = deps;` then `d.time.now()` is invisible; `markAllUsed` only special-cases identifiers literally named `deps` passed to calls/returns/spreads, so `const alias = deps; return alias;` fails to mark all as used (false positive: reports unused deps that are actually forwarded via alias).
- Optional chaining `deps?.time?.now()` — `MemberExpression` handler doesn't check for `OptionalMemberExpression`/`ChainExpression` wrapping; TS-ESLint typically still parses `?.` as `MemberExpression` with `optional: true`, so likely fine, but worth confirming since `node.computed` guard only excludes bracket access, not chain nodes.
- Nested function reference to outer `deps` from a param shadow: if an inner function also declares its own `deps` parameter (shadowing), `nearestTrackedFunction` still walks up correctly, but a `CallExpression` argument `deps` inside the inner function marks the *inner* tracked function's dependencies all-used even if the inner `deps` is unrelated in type — since `markAllUsed` only checks `node.name === "deps"`, not identity/scope resolution. Two nested functions both named `deps` params of different wrapper types get cross-contaminated.

### sort-dependency-types — Low/Medium
- Reasonable and narrowly scoped; only flags intersections where every member is directly a `*Dep`/`Partial&lt;*Dep&gt;` reference, explicitly bailing on mixed refinement intersections — a defensible, low-risk design.
- Medium: doesn't handle nested intersections written across multiple lines/parenthesized groups, e.g. `(TimeDep &amp; LoggerDep) &amp; FileSystemDep` — `TSIntersectionType.types` for the outer node includes a `TSParenthesizedType`(or the nested `TSIntersectionType` itself depending on parser flattening), which `dependencyReferences` doesn't unwrap for parens, so this legal equivalent form is silently skipped (false negative) rather than sorted or explicitly documented as ignored.
- Doc gap: doesn't state whether relative ordering is case-sensitive/locale-dependent (`localeCompare` behavior for mixed-case wrapper names like `HTTPClientDep` vs `HttpClientDep`) — minor.

### named-imports — Low
- Solid, generic, uses minimatch glob options rather than a name list — good example of the pattern the owner wants. Minor gap: `ImportDefaultSpecifier` combined with named specifiers in one declaration (`import Foo, { bar } from "x"`) reports only the default specifier node — correct, but doc's "Some packages... require a default or namespace shape" examples don't show mixed import statements, worth a doc example.
- No handling of `export { default } from "./x"` / `export * as ns from "./x"` re-export shapes, which structurally mirror default/namespace imports but bypass the rule entirely (false negative, medium) since only `ImportDeclaration` is visited, not `ExportAllDeclaration`/`ExportNamedDeclaration` with `source`.

### prefer-arrow-functions — Medium
- Option surface (`allowedNames`, `allowedFiles`) is exactly the "long list of names/files" anti-pattern the owner wants to avoid; acceptable as escape hatches but the doc frames them as first-class recommended options rather than last-resort.
- False negative: `allowRecursive`/`allowHoisted` detection resolves via `context.sourceCode.getScope(node).upper?.set.get(name)` — for a `FunctionDeclaration` this is the function's own name typically bound in the *enclosing* scope, but for hoisting checks this only looks at `upper` scope, missing named function expressions bound inside their own scope (`const f = function fact(n) { return n &lt;= 1 ? 1 : n * fact(n-1); }` — the inner `fact` binding lives in the function-expression's own scope, not `upper`), so `allowRecursive` won't recognize this classic recursive-named-function-expression pattern (false negative — rule reports `useArrow` even with the option enabled, or worse, silently mis-detects).
- Class methods and object method shorthand functions aren't function declarations/expressions in the AST sense checked (`FunctionExpression` handler does catch object/class method values, but reports "useArrow" for `class Foo { method() {} }internally — wait: those are `FunctionExpression` nodes too under `MethodDefinition`/`Property`, so `useArrow` misfires on class methods, which cannot be arrow functions in JS at all. This is a **false positive of high severity**: e.g. `class Repo { getAll(): Item[] { return []; } }` — the method's value is a `FunctionExpression`, `isAllowed` returns false unless excepted, and the rule reports "Use an arrow function instead of the function keyword" for a construct where that fix is a syntax error (class methods can't be declared as arrow-typed class fields without changing semantics/API). Docs never mention or exempt class methods.

### prefer-interface-over-type — Low
- False negative: `type Foo = { a: string } | { b: string }` — a union of object literals — isn't flagged (type alias, but `typeAnnotation.type` is `TSUnionType`, not `TSTypeLiteral`), consistent with doc's stated exception for unions, fine.
- False negative: `type Foo = SomeGeneric&lt;{ a: string }&gt;` (object literal wrapped in a generic) also isn't caught — reasonable, not documented as excluded but low severity.
- Straightforward, low risk overall; good example of a structural, non-naming rule.

### prefer-readonly-types — Medium
- `TSTypeReference` check only flags bare `Array`/`Map`/`Set`/`Record` by identifier name; misses index-signature interface members and computed keys — minor.
- Medium false negative: `collectionScope: "contracts"` walk (`isContractType`) stops climbing at the first `VariableDeclarator`/function boundary, meaning a `Map` declared as a *return type* of an interface method (`interface Foo { getCache(): Map&lt;string, number&gt;; }`) — its ancestor chain hits `TSInterfaceDeclaration` before any `VariableDeclarator`, so it's correctly caught; but a `Map` used inside a function parameter type of a contract method type literal nested inside a `type Handler = (m: Map&lt;string,string&gt;) =&gt; void` — the walk hits `TSTypeAliasDeclaration` fine. Low-impact edge cases; the rule's logic is mostly sound and generic. Docs are accurate.

### top-down-declarations — Medium
- `declarationRank` treats `ClassDeclaration` the same as `VariableDeclaration` (rank 3, "private implementation details") even when exported (`export class Foo {}` triggers rank 2 via the `ExportNamedDeclaration` branch, correctly), but a *non-exported* `abstract class` used as a shared contract (common in OO-style TS) is demoted to "implementation detail" tier alongside truly private helpers — an architecturally significant class contract gets the same rank as leaf helpers, no distinction. Low/medium.
- `preserveRuntimeDependencies` walk only inspects `scope.variables` in the *module* scope for identifiers referenced inside the out-of-order statement; it doesn't account for function declarations that reference each other via hoisting call graphs indirectly (a function ranked 3 that's referenced by an exported const at rank 2 defined earlier, forcing a specific order) — the check is one-directional (does statement depend on something earlier) but not "does something earlier depend on this being after it," so it can still suggest reorderings that break correct call-order presentation in edge cases. Medium, hard to hit in practice.
- Docs are accurate and match implementation reasonably well; no major doc/behavior mismatch found here.

- **Medium:** None of the `dependency-*` docs disclose the hard-coded `*Dep` regex as a *configuration* limitation — they present it as an architectural convention rather than flagging that it's the sole detection mechanism (no type-checker fallback), which is the single biggest blocker to the stated goal of "generic, non-Evolu-specific" rules.
- **Low:** All docs reference `evolu.dev` URLs exclusively — ties the plugin narratively to one project despite the stated goal of being a generic architecture plugin; consider decoupling doc language/URLs from Evolu-specific docs pages, or at least adding a generic architectural rationale independent of the external link.</result>
